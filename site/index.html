structure Person where
  email : Key String          -- owns email @key
  name  : String
  age   : Option Int64 := none
  deriving Entity

structure Friendship where
  a : Role "friend" (Ref Person)
  b : Role "friend" (Ref Person)
  deriving Relation

def befriend : Tx .write Unit := do
  let ann ← Entity.insert { email := "ann@example.com", name := "Ann" : Person }
  let bob ← Entity.insert { email := "bob@example.com", name := "Bob" : Person }
  discard <| Relation.insert { a := ann, b := bob : Friendship }

def names : Tx .read (Array (Col "n" String)) :=
  query typeql!"match $p isa person, has name $n;"
Why TypeDB and Lean

Two type systems that should meet

TypeDB types your data

TypeDB is a polymorphic database. Its schema declares entities, relations, attributes and the roles they play, with inheritance, and the server rejects data that does not fit. TypeQL queries are checked against that schema before they run.

Lean types your program

Lean 4 is a functional language and proof assistant with dependent types. Its type checker can carry facts that most languages leave to tests: which transaction may write, which values a query may contain, what shape a row has.

Most database clients throw both away at the boundary: queries become strings, results become untyped maps, and mistakes show up at run time. typedb-lean keeps the types on both sides and connects them, so a mismatch between your code and your database is caught by the compiler, or once at start-up by schema verification.

Types everywhere

One definition, checked on both sides

A Lean structure is the source of truth. It generates the TypeQL schema, decodes rows, and is verified against the live database.

TypeDB schema

define
  attribute company, value string;
  attribute salary, value decimal;
  entity employee, sub person,
    owns company @card(1..1),
    owns salary @card(1..1);
  relation endorsement,
    relates endorsed, relates endorser;
  friendship plays endorsement:endorsed;
  person plays endorsement:endorser;
Tx

Typed transactions

Tx .read α, Tx .write α and Tx .schema α are different types. An insert inside a read transaction does not compile.

{}

Typed queries

typeql!"… {value} …" escapes every value through ToTypeQL, and reads the query's mode off its text. User data cannot change a query's structure.

⟨⟩

Typed results

Rows decode straight into structures with deriving FromRow; fetch documents through FromJson. A wrong column type is a typed decode error.

=

Exact values

decimal is an exact Decimal, dates are Std.Time, duration keeps months, days and nanoseconds apart. Nothing is rounded through a float.

ORM

A lightweight ORM

deriving Entity and deriving Relation: inserts, reads, updates, deletes, subtypes, relations in roles, polymorphic reads.

↑↓

Migrations

Versioned up and down steps with history and checksums stored in the database. A step can change the schema and backfill data atomically.

Mistakes become compile errors

The compiler knows what a transaction may do

Every query carries the weakest transaction mode that may run it, inferred from its text: define needs schema, insert needs write, a match needs only read. Every operation asks for a proof that the current mode allows it.

Read helpers lift into write transactions on their own, and a helper can be generic over any mode strong enough to run it.
