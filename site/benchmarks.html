Performance

typedb-lean vs the Rust driver

typedb-lean wraps TypeDB's official C driver, which is itself built on the Rust driver. The question is what the Lean layer costs. The answer: nothing measurable on scans, lookups and inserts, and less than the Rust baseline under concurrency.

Workloads

The benchmark loads 100,000 person entities, each with an email key, a name and an age. Then it runs the same four workloads with this library and with a Rust program that uses typedb-driver directly (bench/rust). Both clients warm up first.

define
  attribute email, value string;
  attribute name, value string;
  attribute age, value integer;
  entity person, owns email @key, owns name, owns age;
  • Scan. One read transaction runs match $p isa person, has email $e, has name $n, has age $a; limit 100000; and decodes every row into a structure of three fields. In Lean that is query (α := Person) with deriving FromRow; in Rust, a decode function that reads the three columns.
  • Point lookup. 1,000 lookups by email, each in its own read transaction, so the time includes opening and closing the transaction. p50 and p99 are taken over all of them.
  • Bulk insert. A fresh database, then one write transaction with 10,000 separate insert queries and a commit.
  • Concurrent reads. 16 read transactions at once, each scanning 10,000 rows. Lean uses EAsync.concurrentlyAll over Driver.run; Rust uses 16 scoped threads.

Why a wrapper can match the native driver

Calling Rust through C from Lean adds a boundary crossing per call. The library makes those crossings rare and cheap:

  • Batched decoding. A RowDecoder knows its columns and what it needs from each (a value, a type label or an IID). One native call returns those for up to batchSize rows, with no intermediate object per concept.
  • Prefetch 512. The server streams up to prefetch answers ahead of the client. typedb-lean sets 512 by default; with the C driver's smaller default, a scan waits on the network.
  • Closing in the background. Closing a transaction does not wait for the driver to finish, like the Rust driver's drop.
  • Loops compile to loops. Tx is a ReaderT over EIO, so for in a transaction body compiles to a plain loop.
  • Dedicated threads. Each async transaction blocks only its own thread, and one driver connection multiplexes all of them.

The Rust baseline uses the driver's defaults. It is not tuned, so read the concurrency result as "the Lean layer adds no contention", not as "Lean is faster than Rust".

Targets and CI

The benchmark is a test, not just a report. It fails unless:

  • the scan reaches at least 80% of the Rust driver's rows per second, and
  • the lookup p50 is at most 1.1× the Rust driver's.

CI runs lake exe bench --ci on Linux x86_64 for pushes to main and pull requests: 20,000 rows, 300 lookups and 2,000 inserts, with the targets relaxed by another 10% for shared runners.

Reproduce

You need Docker, a Rust toolchain and protoc. Without TYPEDB_ADDRESS, the benchmark starts a typedb/typedb container at the pinned version and removes it afterwards.

lake exe bench              # full sizes, enforces the targets, writes bench/report.json
lake exe bench --ci         # reduced sizes, targets relaxed by 10%
lake exe bench --profile    # also times draining, fetching and decoding separately
TYPEDB_ADDRESS=127.0.0.1:1729 lake exe bench   # use a server you already run

Caveats

  • These numbers are from one laptop with the server in Docker. Absolute values depend on the machine and the network; the ratios are what the benchmark checks.
  • Bulk insert time is dominated by the server, which is why both clients take the same time. The benchmark's loader puts 100 entities in each insert query to cut round trips; the measured workload deliberately does not.
  • The upstream driver (3.14.0) keeps about 600 bytes per transaction it has opened, in its Rust and C APIs alike, so processes that open millions of transactions grow accordingly.
